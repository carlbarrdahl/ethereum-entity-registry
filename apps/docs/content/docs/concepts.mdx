# Concepts

The Entity Registry is built on a small set of composable primitives. This page explains the mental model. For precise behavior, see [Requirements](/docs/requirements).

## Identifiers

An **identifier** is a bytes32 hash derived from a `(namespace, canonicalString)` pair:

```
id = keccak256(abi.encode(namespace, canonicalString))
```

Examples:

- `keccak256(abi.encode("github", "org/repo"))` — a GitHub repository
- `keccak256(abi.encode("dns", "example.com"))` — a DNS domain

`abi.encode` (not `abi.encodePacked`) is used to prevent collisions between pairs that share a common packed concatenation.

You can compute this locally — no RPC call needed:

```typescript
import { toId, canonicalise } from '@ethereum-entity-registry/sdk';

const id = toId('github', canonicalise('Org/Repo')); // lowercased to "org/repo"
```

## Namespaces

A **namespace** scopes identifiers to a class of off-chain identity. Each namespace has its own canonicalisation rules and a registered verifier contract.

Namespace labels are exact byte strings and must match `[a-z0-9-]+` (lowercase ASCII). For example, `github` is valid, while `GitHub` is a different string and non-compliant.

| Namespace | Canonical string                  | Example       |
| --------- | --------------------------------- | ------------- |
| `github`  | `owner/repo` (lowercase)          | `org/repo`    |
| `dns`     | apex domain (lowercase, no `www`) | `example.com` |

The contract does not enforce `canonicalString` canonicalisation — it hashes whatever strings are passed. Consistency between funders and claimants is the caller's responsibility. The SDK's `canonicalise()` function applies the baseline rule (lowercase + trim).

## Deposit Addresses

Within a given registry or factory deployment, every identifier has a **deterministic deposit address** — an `IdentityAccount` proxy derived via CREATE2. The address is:

- **Stable**: computed from the identifier and deployment address, independent of whether the account is deployed
- **Computable offline**: derivable from the identifier and registry address without an RPC call
- **Upgrade-safe**: address does not change when the account implementation is upgraded via the beacon

Funders send ERC-20 tokens directly to this address. Funds accumulate whether or not the identifier has been claimed.

If multiple factories are used, the same identifier can have different valid account addresses under different deployments. Ecosystems that want one canonical deposit address per identifier must coordinate on a canonical deployment.

The SDK handles address derivation internally:

```typescript
const state = await sdk.registry.resolve("github.com/org/repo", tokenAddress);
// state.depositAddress — the deterministic identity account address
```

## Claiming

To **claim** an identifier, the owner submits a cryptographic proof to the registry. The registry delegates verification to the namespace's registered verifier contract.

```
Owner → registry.claim(namespace, canonicalString, proof)
             │
             ▼
     verifier.verify(id, msg.sender, proof)
             │
       valid? │
             ▼
    owners[id] = msg.sender
    emit Claimed(...)
    deploy identity account if needed
```

A claim is rejected if:

- The identifier is already claimed
- No verifier is registered for the namespace
- The proof is invalid (wrong signer, expired, wrong claimant)

## Verifiers

A **verifier** is a contract that implements `IVerifier.verify(id, claimant, proof)`. The registry owner registers one verifier per namespace via `setVerifier`.

The current oracle verifier (`OracleVerifier`) uses EIP-712 typed signatures. The backend oracle:

1. Confirms ownership off-chain (GitHub OAuth, DNS TXT record)
2. Signs `{id, claimant, expiry}` with a trusted key
3. Returns the signature as the `proof` bytes

The EIP-712 domain binds the proof to a specific registry address and chain ID, preventing cross-deployment and cross-chain replay. Proofs expire to prevent indefinite replay.

```
DnsVerifier    GitHubVerifier
     │               │
     └───────┬────────┘
             │
        OracleVerifier (base)
             │
       verify(id, claimant, proof)
             │
    recover signer from EIP-712 sig
    check expiry + signer == trustedSigner
```

## Identity Accounts

An **IdentityAccount** is a per-identifier `BeaconProxy` deployed via CREATE2. It:

- Holds ERC-20 tokens and native ETH deposited by funders
- Provides an `execute(target, data, value)` function that lets the owner interact with any external contract
- Routes all actions through the registry's `ownerOf(id)` check — in the base model, only the registered owner can call `execute`

The account is deployed lazily — automatically when the owner claims, or by anyone calling `deployAccount(id)`. Funders can send tokens to the deposit address before it's deployed; the address is always the same.

```typescript
// Transfer ERC-20 tokens out
const { target, data } = sdk.account.encodeERC20Transfer(
  tokenAddress,
  recipient,
  amount,
);
await sdk.account.execute(accountAddress, target, data);

// Withdraw from a Splits Warehouse
const call = sdk.account.encodeWarehouseWithdraw(
  warehouseAddress,
  accountAddress,
  tokenAddress,
);
await sdk.account.execute(accountAddress, call.target, call.data);
```

The `execute` pattern makes the identity account a general-purpose smart account — any future protocol integration works without upgrading the contract.

### Fund Reclaim (Optional Extension)

Some deployments add a **reclaim address** and **deadline** as an implementation extension. If the identity is never claimed, the platform can recover funds after the deadline passes.

```typescript
// Platform initialises the SDK with a custom AccountFactory
const sdk = new EntityRegistrySDK(walletClient, undefined, {
  accountFactory: '0xPlatformFactory...',
});

// Deploy accounts using a platform-specific factory
await sdk.registry.deployAccount(id);
// or batch:
await sdk.registry.deployAccounts([id1, id2, id3]);

// After the deadline, if still unclaimed, reclaim via execute (same patterns as owner)
const to = await sdk.account.reclaimTo(accountAddress);
const amount = /* token balance at accountAddress, from your RPC */;
const { target, data } = sdk.account.encodeERC20Transfer(tokenAddress, to, amount);
await sdk.account.execute(accountAddress, target, data);
```

The reclaim extension follows these rules:

- Once the identity is **claimed**, the owner controls all funds via `execute`. The reclaim path is blocked.
- The reclaim path only works while the identity is **unclaimed** and the **deadline has passed** — `reclaimTo` uses `execute` with the same calldata patterns as the owner (e.g. `encodeERC20Transfer`, `encodeWarehouseWithdraw`).
- If reclaim is used, platforms should configure it atomically with deployment to avoid front-running the initial `setReclaim` call.

## Aliases

**Aliases** link multiple identifiers to a single owner, so `ownerOf(aliasId)` resolves to the primary owner. This allows a GitHub repo and its associated DNS domain to share a single identity.

```typescript
// Link "dns:example.com" as an alias for "github:org/repo"
await sdk.registry.linkIds(primaryId, [aliasId]);

// Both now resolve to the same owner
await sdk.registry.ownerOf(primaryId); // → 0x...
await sdk.registry.ownerOf(aliasId); // → same 0x...
```

Rules:

- Only one level of indirection — no alias chains
- All identifiers must already be claimed by the same address
- Alias accounts remain separate; funds in each accrue independently
- Unlinking restores each identifier to independent ownership

## Resolving an Identifier

The SDK provides a convenience method to resolve full state in parallel:

```typescript
const state = await sdk.registry.resolve("github.com/org/repo", tokenAddress);
// state.id             — bytes32 identifier
// state.depositAddress — where funders send tokens
// state.owner          — null if unclaimed
// state.balance        — current ERC-20 balance at deposit address

// Also accepts other formats:
sdk.registry.resolve("github:org/repo");
sdk.registry.resolve("https://github.com/org/repo");
sdk.registry.resolve("example.com");
```

## Design Principles

| Principle                   | Implementation                                                                                          |
| --------------------------- | ------------------------------------------------------------------------------------------------------- |
| **No prior setup required** | Funders can send tokens before the owner has ever interacted with the protocol                          |
| **Permissionless**          | Anyone can deploy identity accounts or send tokens                                                      |
| **Non-custodial**           | In the base model, only the registered owner can execute actions through the identity account           |
| **Upgradeable**             | Beacon pattern allows fixing bugs without changing any deposit address                                  |
| **General-purpose**         | `execute` enables any on-chain interaction without contract upgrades                                    |
| **Pluggable verification**  | Verifiers are swappable per namespace — DNSSEC on-chain verification can replace the oracle model later |
