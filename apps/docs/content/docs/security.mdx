# Security

## Trust Model

The registry contract has no privileged operators beyond the admin key, whose only authority is registering and replacing verifier contracts via `setVerifier` and upgrading the identity account implementation via `upgradeAccountImplementation`. It holds no funds. The trust assumptions are in the verifiers and the identity account module.

### Trust Assumptions by Actor

| Actor              | Trust Level          | Capabilities                                                                      |
| ------------------ | -------------------- | --------------------------------------------------------------------------------- |
| **Registry owner** | Trusted admin        | Can update verifiers, upgrade account impl via beacon                             |
| **Oracle signer**  | Trusted for proofs   | Signs claim proofs after off-chain verification; cannot affect existing ownership |
| **Claimants**      | Must prove ownership | Can claim only with a valid, unexpired oracle proof                               |
| **Funders**        | Trustless            | Send tokens to deposit addresses; some deployments may additionally configure reclaim via `AccountFactory` |
| **Owner**          | Authenticated        | Controls the base `execute` path on their identity account                        |

### Oracle Verifiers (Current)

A trusted backend confirms ownership off-chain and issues a signed proof. The trust model is equivalent to trusting that backend service.

Mitigations:

- The signing key is rotatable via `setTrustedSigner` without changing the registry or invalidating existing claims
- A compromised key allows claiming any unclaimed identifier in affected namespaces, until the key is rotated
- Signing keys should be held in an HSM with defined rotation procedures

### ZK Verifiers (Migration Path)

Ownership is proven cryptographically on-chain. No trust assumption beyond the proof system itself.

- **GitHub:** zkTLS proof of the GitHub API response (vlayer, TLSNotary)
- **DNS:** DNSSEC proof — ENS's `DNSSECImpl` can be wrapped directly as an `IVerifier`

The migration path: deploy a new `IVerifier` implementation and call `registry.setVerifier(namespace, newVerifier)`. Existing claims are unaffected.

## Security Considerations

### Proof Replay

EIP-712 domain separation binds proofs to a specific chain and registry deployment. Proofs include a claimant address and an expiry timestamp (default 1 hour). Within the TTL window, the same proof could be re-submitted by the same claimant after a revoke. This is accepted at the contract level and mitigated by the backend issuing fresh proofs on each request.

### Identifier Collisions

`abi.encode` (length-prefixed) prevents collisions between different namespace/string pairs that produce the same packed concatenation — e.g. `"githu"+"borg/repo"` vs `"github"+"org/repo"`.

### Normalisation

Namespace labels are lowercase ASCII matching `[a-z0-9-]+`. Rules for `canonicalString` remain namespace-specific and are enforced by verifiers, not globally by the registry. Frontends and verifiers share responsibility for consistent canonicalisation.

### Oracle Key Compromise

A compromised signing key allows claiming any unclaimed identifier in all namespaces sharing that verifier, until the key is rotated. Key storage and rotation procedures are required for production deployments.

### Account Upgradeability

The beacon is owned by the registry. Upgrading the account implementation simultaneously affects the logic behind all deployed proxies. The admin key is a critical trust assumption for the identity account module, independent of the verifier admin key.

### Counterfactual Address Griefing

Deposit addresses are public and computable by anyone. An adversary could pre-deploy account proxies for identifiers at a gas cost, without any effect on correctness — the deposit address and accumulated funds are unaffected. This is a nuisance, not a security issue.

### Reclaim Extension Configuration

The reclaim path is an implementation extension, not part of the minimal owner-only account model. In this repository's implementation, `setReclaim` is first-caller-wins when `reclaimTo` is unset. An adversary who monitors the mempool could front-run a platform's `setReclaim` call. Platforms SHOULD configure reclaim atomically with deployment, for example through an `AccountFactory` or wrapper contract.

### Reclaim After Claim-and-Revoke

If an identity is claimed and then revoked, a previously configured reclaim address regains temporary `execute` rights (assuming the deadline has passed and the identity is unclaimed). This is by design — if the owner chose not to withdraw before revoking, the funder should be able to recover.

### No Ownership Transfer

There is no `transferOwnership` function. The only way to change the registered address is to revoke and re-claim with a fresh proof. This ties the registered address to the actual identity owner at claim time, but means wallet rotation requires a new verification round-trip.

### Identifier Renames (Stale Claims)

Off-chain identifiers can change their canonical string — a GitHub repo can be renamed, a package can move to a new scope, a domain can be transferred. When this happens, the old `bytes32` identifier and the new one are completely unrelated hashes. The old identifier still resolves to the original owner; the new identifier resolves to `address(0)`.

**Recommended migration:**

1. **Claim** the new identifier — the owner still controls the entity, so any verifier (oracle or ZK) can produce a valid proof for the new canonical string
2. **Link** the old identifier as an alias of the new one via `linkIds(newId, [oldId])`

After linking, both identifiers resolve to the same address. Protocols that cached the old identifier continue to work.

**If the owner doesn't act**, the old claim becomes stale. Two future mechanisms can address this:

- **Time-bounded claims**: Verifiers enforce expiring proofs, so stale claims die naturally when the owner can no longer re-verify
- **Challenge mechanism** (future ERC): A third party submits a counter-proof (oracle-signed or ZK) showing the on-chain registrant no longer controls the off-chain entity

See the [FAQ](/docs/faq) for worked examples.

## Non-Custodial Properties

In the base model, `IdentityAccount` restricts `execute` to the registered owner via `registry.ownerOf(id) == msg.sender`. This repository's implementation also supports an optional reclaim path while the identity is unclaimed. The registry owner can change verifiers or upgrade the account implementation, but cannot bypass those authorization checks directly.

## Known Limitations (POC)

| Limitation                | Risk                                      | Production Solution                                          |
| ------------------------- | ----------------------------------------- | ------------------------------------------------------------ |
| Oracle-based verification | Requires trusting the oracle backend      | Replace with DNSSEC on-chain verification via ENS DNSSECImpl |
| Single trusted signer     | Key compromise allows fraudulent claims   | Threshold signatures or HSM                                  |
| No claim timelock         | Fresh claims immediately enable execution | Add claim cooldown for large deposits                        |
| Fee-on-transfer tokens    | Balance calculations off                  | Explicit token allowlist or deposit accounting               |
